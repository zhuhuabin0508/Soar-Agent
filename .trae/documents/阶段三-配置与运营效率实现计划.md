## 子任务 3：告警处置闭环

### 目标
告警列表补充工单流：状态机（待确认→处置中→已关闭，支持退回）、单条/批量处置、指派处理人、处置备注留痕、详情抽屉展示处置时间线。操作记录不可删除（等保审计）。

### 状态机设计
利用现有 `deal_status` 值，定义状态流转规则：
- `0`(未处置/待确认) → `70`(处置中)
- `70`(处置中) → `20`(已关闭/已完成)
- `70` → `0`(退回待确认)
- `20` → `70`(重新打开)
- 终态可选：`30`(已加白)/`40`(已驳回)/`50`(已忽略)/`60`(已遏制)/`80`(误报)

### 后端改动
- `backend/app/models/alert_event.py`：新增 3 列 — `assignee_id`(Integer nullable)、`assignee_name`(String(64) default="")、`handled_at`(DateTime nullable)
- `backend/app/models/alert_handle_log.py`（新建）：`AlertHandleLog` 模型
  - `id`, `alert_id`(index), `action`(String: status_change/assign/comment/reopen/close), `from_status`(int), `to_status`(int), `from_assignee`(String), `to_assignee`(String), `operator_id`(int), `operator_name`(String), `comment`(Text), `created_at`(DateTime index)
  - 唯一约束无 — 同一告警可有多条日志（时间线）
- `backend/app/models/__init__.py`：注册 AlertHandleLog
- `backend/app/api/v1/alerts.py`：新增 3 个端点
  - `POST /alerts/{id}/handle`：请求体 `{ to_status, assignee_id, comment }` — 校验状态机合法性，更新 AlertEvent，写 AlertHandleLog，写审计日志
  - `POST /alerts/batch-handle`：请求体 `{ alert_ids: [], to_status, assignee_id, comment }` — 批量处置
  - `GET /alerts/{id}/handle-logs`：返回时间线列表（按 created_at desc）
  - `_serialize` 扩展：列表/详情均增加 `assignee_id`/`assignee_name`/`handled_at`
- `backend/app/main.py` 或启动钩子：`ensure_columns` 补齐 AlertEvent 新增 3 列

### 前端改动
- `frontend/src/api/alert.js`：新增 `handle(id, body)`/`batchHandle(body)`/`handleLogs(id)` 方法
- `frontend/src/pages/AlertList.jsx`：
  - DataTable 开启 `selectable`，添加全选/勾选
  - 选中时底部浮出批量操作栏：批量处置按钮（状态选择+指派+备注）
  - deal_status 列 Badge 增加指派人显示
- `frontend/src/pages/AlertDetailDrawer.jsx`：
  - 新增第 7 个 Tab "处置记录"
  - Tab 内容：当前状态 + 指派人 + 处置表单（状态下拉 + 指派人下拉(用户列表) + 备注输入 + 提交按钮）+ 时间线列表（操作/操作人/时间/备注/状态变更）
- 状态流转校验：前端根据状态机规则禁用不可达的目标状态选项
