# 日志来源条目模型（log_source_entries）实施计划

## Context

当前 `log_receivers` 表把"监听端点、设备绑定、解析策略"揉在一起：同一渠道下所有日志共用一套流水线配置，来源 IP 仅是记录字段。用户期望分层模型——**接收器只管监听端点**（如 `0.0.0.0:514`），**日志到达后按来源 IP 自动生成"来源条目"**（如 1.1.1.1 发来日志即生成该 IP 条目），管理员点击条目可独立配置解析策略、富化策略、过滤策略。

已确认的设计决策：
1. **仅监听型渠道启用条目**（syslog / snmp_trap / netflow / pcap）；拉取型（kafka / jdbc / rest_api / file_tail）保持渠道级策略不变
2. **自动发现即生效**：首见立即创建条目，未配置时走接收器默认（日志零丢失）
3. **条目管理入口**：渠道列表行展开"来源条目"抽屉，点击条目打开配置弹窗

关键验证结论（决定实现方式）：
- `pipeline/runner.py` L119-121 缓存"同渠道只保留最新一个"——引入条目级配置后多条目会互挤缓存，**必须改为 LRU**
- `pipeline/parser_stage.py` L44 `pinned_id = receiver.get("strategy_id")`——条目级 strategy_id 通过合并进 receiver dict 即天然形成优先级链 **条目 → 渠道 → 设备 → 自动匹配**，parser_stage 零改动
- `DeviceReceiveLog` 已有 `source_ip` 列，明细日志零迁移
- 新表经 `models/__init__.py` 注册后由 `main.py` 的 `Base.metadata.create_all` 自动建表
- pcap 适配器 `source_ip=None`（批量打包），暂无条目爆炸风险，但渠道级"条目自动发现"开关仍需支持（防未来按流聚合后爆炸）

## 阶段 1：模型与迁移

**新建 `backend/app/models/log_source_entry.py`**（并在 `models/__init__.py` 注册）：

```python
class LogSourceEntry(Base):
    __tablename__ = "log_source_entries"
    id            = Column(Integer, primary_key=True, autoincrement=True)
    receiver_id   = Column(Integer, nullable=False, index=True)
    source_ip     = Column(String(64), nullable=False)
    name          = Column(String(128), nullable=False, default="")   # 默认=source_ip
    device_id     = Column(Integer, nullable=True, index=True)        # 首见自动按 devices.ip_address 匹配
    enabled       = Column(Integer, nullable=False, default=1)
    strategy_id   = Column(Integer, nullable=True)                   # 条目级手动策略（优先级链最前）
    entry_config  = Column(Text, nullable=False, default="{}")       # {"pipeline":{...}} 条目级流水线覆盖
    auto_created  = Column(Integer, nullable=False, default=1)
    received_count = Column(Integer, nullable=False, default=0)
    last_received_at = Column(DateTime, nullable=True)
    created_at / updated_at
    __table_args__ = (UniqueConstraint("receiver_id", "source_ip", name="uq_log_source_entry_recv_ip"),)
```

`log_receivers.adapter_config` 增两个约定键（**无需加列**）：`entry_discovery`（bool，监听型默认 true / 拉取型 false）、`entry_max_count`（默认 1000，防爆炸）。

## 阶段 2：自动发现机制（entry_registry）

**新建 `backend/app/core/log_receiver_manager/entry_registry.py`**（进程级单例，仅事件 worker 使用）：

- `_cache: dict[(rid, ip), dict]` 条目配置快照（entry_id/strategy_id/entry_config/device_id/enabled），hit 零查库；条目带 60s TTL（跨 worker 最终一致）
- `_pending: set[(rid, ip)]` 首见去重；`_stats: dict[(rid, ip), [count, last_at]]` 统计缓冲
- `resolve(rid, ip, receiver)`：缓存 miss → 短会话一次查 `log_source_entries` → 无则（发现开关开且未超上限）INSERT 并顺带 `SELECT id FROM devices WHERE ip_address=:ip` 绑定设备；INSERT 失败仅记日志返回 None，**事件继续走渠道默认，零丢失**
- `bump(rid, ip)`：内存计数；`flush()`：批量 UPDATE 累加 received_count/last_received_at，挂到 `runtime.py` `_run_health_check` 循环（60s）末尾，不新增线程；`invalidate(rid, ip)`：API 更新后同进程立即失效

**注入点：`pipeline/runner.py` 的 `run_pipeline_for_event`**（worker 回调内、`for_receiver` 之前）：

```python
receiver = event.receiver or {}
if event.source_ip and receiver.get("protocol") in {"syslog", "snmp_trap", "netflow", "pcap"}:
    entry = entry_registry.resolve(event.receiver_id, event.source_ip, receiver)
    if entry is not None:
        entry_registry.bump(event.receiver_id, event.source_ip)
        if not entry.get("enabled"):
            return                                   # 条目停用=丢弃
        receiver = merge_receiver_entry(receiver, entry)
PipelineRunner.for_receiver(receiver).run(event)
```

首见 INSERT 用独立 `SessionLocal()`（模仿 `sink._bump_counts` 模式），不占事件主会话，与背压/拉取游标无关。

## 阶段 3：配置合并与缓存键扩展

`entry_registry.merge_receiver_entry(receiver, entry)`：浅拷贝 receiver dict；`strategy_id`/`device_id` 非空时覆盖；`entry_config.pipeline` 与 `adapter_config.pipeline` 用 runner 已有 `_deep_merge` 合并。

**`runner.py for_receiver` 缓存改造**（关键）：缓存键 `(rid, source_ip or "", config_hash)`；删除 L119-121 的"同渠道只留最新一个"，改容量上限 LRU（每 rid 保留最近 32 个、全局 512，dict 保序 pop 最旧）——否则多条目互挤导致每条日志重建 Runner。

## 阶段 4：API（`backend/app/api/v1/log_receivers.py`）

- `GET /log-receivers/{rid}/entries`：分页列表（search 过滤 ip/name），带统计与配置状态
- `PUT /log-receivers/entries/{eid}`：更新 name/device_id/enabled/strategy_id/entry_config，成功后 `entry_registry.invalidate(rid, ip)`
- `DELETE /log-receivers/entries/{eid}`；`POST /log-receivers/{rid}/entries/batch-delete`
- 现有 `GET /receive-logs` 加 `source_ip` query 参数（条目明细复用）
- `_serialize` 增 `entries_count`（一次 GROUP BY），前端据此显示"来源条目(N)"

## 阶段 5：前端（`frontend/src/pages/devices/LogReceivers.jsx` + `api/client.js`）

- client.js `logReceivers` 增 `entries(rid, params)/entryUpdate/entryRemove/entryBatchRemove`
- 渠道表格行（监听型协议）操作列加"来源条目(N)"按钮
- 新组件 `LogSourceEntryDrawer`：Modal lg，条目表格（来源 IP/名称/设备/接收量右对齐/最近接收/策略/状态/操作），顶部搜索+批量删除，空态引导；复用 Modal/inputCls/toast 惯例
- 新组件 `SourceEntryFormModal`：名称、绑定设备 select、解析策略 select、启用开关、条目流水线覆盖（filter/enricher 结构化编辑 + 高级 JSON）
- `AdapterConfigSection` 对监听型协议追加"条目自动发现"开关与上限字段（写入 adapter_config.entry_discovery/entry_max_count）

## 阶段 6：测试

**新建 `backend/tests/test_source_entries.py`**：
1. 首见自动建条目 + 设备 IP 绑定；同 IP 二次事件零查库
2. 优先级链：entry.strategy_id > receiver.strategy_id > 设备绑定 > 自动
3. entry pipeline 深合并；不同 source_ip 的 runner 缓存实例共存不互挤（LRU）
4. 未配置条目回退渠道级；发现开关关/超上限不建条目且事件正常处理
5. 统计 flush 累加正确；条目 CRUD API + 批量删除
