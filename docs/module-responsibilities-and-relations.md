# 模块职责与关系梳理

> 适用对象：SOAR 平台「智能体编排」体系下的**智能体 / 工作流 / 技能 / 工具 / 知识库**五大模块。
> 目的：厘清各模块的定位、边界、挂载关系与当前存在的问题，为后续重构与排障提供统一认知。
> 注：本平台当前所有智能体均为 `hermes` 引擎。

---

## 一、总览：五个模块分属三个层级

这五个模块看似并列（都在侧边栏「智能体编排」分组下），**但它们在概念上不属于同一层**，这是"乱"的主要来源。

| 层级 | 模块 | 一句话定位 | 谁来用它 |
|------|------|-----------|----------|
| 执行编排层 | **智能体 Agent** | 一次"对话/研判"的完整执行者（含模型、提示词、可调能力） | 用户对话、工作流节点、封禁决策 |
| 执行编排层 | **工作流 Workflow** | 一组有序节点的自动化编排（可含 AI 分析/HTTP/条件分支/Webhook） | 告警入库、定时、事件触发 |
| 能力层 | **工具 Tool** | 智能体/工作流可调用的具体动作（code/http/framework） | 被智能体、工作流、技能引用 |
| 内容认知层 | **技能 Skill** | 一段注入进提示词的自然语言指导（教模型"怎么想/怎么做"） | 仅被智能体注入进 `system_prompt` |
| 内容认知层 | **知识库 Knowledge Base** | 可供检索的文档/向量数据（教模型"知道什么"） | 被智能体引用，生成检索工具 |

**关键认知：**
- 「智能体」是**编排中枢**，它同时引用：模型、系统提示词、**技能**、**知识库**、**工具**、**资产类型**。
- 「工作流」是另一个独立编排单元，它的节点也可以调用「智能体」或「工具」。
- 「技能 / 知识库 / 工具」都是**被引用的资产**，本身不独立运行。

---

## 二、各模块职责与创建入口

### 1. 智能体（Agent）
- **职责**：定义一次智能交互的完整上下文 —— 选模型、写系统提示词、勾选可用的工具/技能/知识库/资产类型、设温度/轮数/记忆。
- **前端入口**：`/agents`（列表）、`/agents/new`（新建）、`/agents/:id/edit`（编辑）。
- **后端模型**：`backend/app/models/agent.py`（`Agent` 表）。
- **引擎**：当前全部为 `hermes`（Hermes 风格 ReAct）。
- **挂载关系**（智能体"引用了谁"）：
  - `model_config_id` → LLM 配置
  - `system_prompt` + `enabled_skills` → 组装后的系统提示词
  - `enabled_kbs` → 生成知识库检索工具
  - `enabled_tools` → 挂载 DB 工具
  - `enabled_asset_types` → 额外驱动资产检索工具
  - `tool_configs` → 工具行为（超时/重试/确认/tool_search/guardrails）

### 2. 工作流（Workflow）
- **职责**：把多个节点串成一条可执行的自动化流程；节点可触发智能体、调 HTTP、条件分支、Webhook 触发、封禁决策等。
- **前端入口**：`/workflows`（列表）、`/editor`（编排）、`/workflows/:id/monitor`（监控）。
- **后端模型**：`backend/app/models/workflow.py`（`Workflow` 表）+ 版本（`workflow_versions`）。
- **注意**：导航「工作流」下还有 **`触发规则`（/ban-workflow/rules）** —— 这是**封禁 IP 专用工作流**的触发规则（告警入库 → 研判 → 封禁），与通用工作流是**两套体系**，易混淆。

### 3. 技能（Skill）
- **职责**：一段纯文本指导，在智能体组装提示词时**注入 `system_prompt`**（教模型流程、判断标准、输出模板）。
- **前端入口**：`/skills`。
- **后端模型**：`backend/app/models/skill.py`（`Skill` 表）。
- **注入机制**：`backend/app/agent/prompt_assembler.py` — 按 `agent.enabled_skills` 加载「启用中」的技能，按 `priority` 降序拼成 `=== 启用技能 ===` 段落注入。
- **注意**：技能**只影响提示词**，不产生可调用动作；「动作能力」必须靠工具。

### 4. 工具（Tool）
- **职责**：智能体/工作流可调用的原子动作。分三种类型：
  - `code`（36 个）：Python 代码动作（安全工具/资产/封禁等）
  - `http`（2 个）：HTTP/OpenAPI 请求
  - `framework`（14 个）：框架级内置动作（delegate_task、clarify、plan、记忆、技能触发等）
- **前端入口**：`/tools`（列表）、`/tools/new`、`/tools/:id/edit`。
- **后端模型**：`backend/app/models/tool.py`（`Tool` 表）。
- **挂载到智能体**：`enabled_tools` 中列出的工具名 → 由 `decision.py`（LangGraph）/ `tool_engine.py`（Hermes）加载。
- **⚠️ 混乱点：资产检索工具的特殊挂载**
  - `search_assets` 既出现在工具表（id=123，code 类型），又被 `decision.py` / `tool_engine.py` 里的 `if name == "search_assets": continue` **跳过**，转而由 **`enabled_asset_types`（智能体勾选的资产类型）** 驱动另一条 `_build_asset_tool` 路径生成。
  - 结果：**"工具表里有这个工具，但你不是靠勾选工具唤醒它，而是靠勾选资产类型唤醒它"** —— 这是很反直觉的设计，也是你排查"配置了却不生效"的根源。
- **⚠️ 混乱点：tool_search 动态隐藏**
  - 当智能体配置 `tool_configs.tool_search.enabled="on"` 时，除核心来源（asset）外的工具会被**延迟进目录**，模型需先调 `tool_search` 才能看到（如研判智能体装配后只剩 search_assets 直接可见，威胁情报/封禁工具全被隐藏）。

### 5. 知识库（Knowledge Base）
- **职责**：上传文档 → 分段/向量化 → 供智能体按 `enabled_kbs` 检索。
- **前端入口**：`/knowledge-base`。
- **后端模型**：`backend/app/models/knowledge_base.py`；处理在 `code/kb_service.py`、`kb_retriever.py`、`chunker.py`、`embedding.py`。
- **挂载到智能体**：`enabled_kbs` 非空时，生成两个检索工具：
  - `search_knowledge_base`（语义检索）
  - `query_kb_file`（Excel/CSV 精确查询）
- 当前库中知识库数量为 0（待建设）。

## 三、模块间的关系图

```
                    ┌──────────────────────────────────────────────┐
                    │              智能体 (Agent)                   │
                    │  编排中枢：决定"谁来干、怎么想、能调什么"      │
                    └───────┬──────────┬──────────┬────────┬───────┘
                            │          │          │        │
          system_prompt+技能 │   模型配置 │   工具    │ 知识库 │ 资产类型
                            ▼          ▼          ▼        ▼       ▼
                       ┌────────┐ ┌────────┐ ┌────────┐ ┌─────────┐ ┌────────┐
                       │  技能  │ │ LLM配置 │ │  工具  │ │ 知识库   │ │ 资产类型 │
                       │(内容层)│ │(连接层) │ │(能力层)│ │ (内容层) │ │(数据层) │
                       └────────┘ └────────┘ └────────┘ └─────────┘ └────────┘

                    ┌──────────────────────────────────────────────┐
                    │              工作流 (Workflow)                │
                    │  节点编排；可调用 [智能体] 和 [工具]           │
                    └──────────────────────────────────────────────┘

    另：触发规则(/ban-workflow/rules) = 封禁专用工作流的触发入口（独立体系）
```

**谁引用谁（一句话总结）：**
- 智能体 → 引用：模型配置、技能、知识库、工具、资产类型
- 工作流 → 引用：智能体、工具
- 技能 / 知识库 / 工具 → **不引用彼此**（均被上层引用）

## 四、当前「乱」的具体问题清单

| # | 问题 | 所在位置 | 影响 |
|---|------|---------|------|
| 1 | 五模块在导航平铺，但分属执行/能力/内容三层 | 前端 `AppShell` 导航 | 概念层级不清，易误以为同一层 |
| 2 | `search_assets` 双轨挂载（工具表 + 资产类型直挂），且工具表路径被 `continue` 跳过 | `decision.py`、`tool_engine.py` | 配置了工具却不一定生效，难以排障 |
| 3 | tool_search 动态隐藏非核心工具 | `tool_search.py`、`tool_engine.py` | 研判智能体看不到威胁情报/封禁等关键工具 |
| 4 | 内置工具迁移为 DB code 工具后，与用户自建工具混在一起 | `seed.py` 的 `HERMES_BUILTIN_TOOLS` / 工具表 | 工具列表冗长、来源难辨 |
| 5 | framework/code/http 三类工具语义差异未对用户讲清 | 工具模型 | 新建工具时选型困惑 |
| 6 | 通用工作流 与 封禁专用工作流（触发规则）并存 | 导航「工作流」下 | 两套工作流概念混淆 |
| 7 | 知识库为 0、技能/工具/资产检索能力存在重复与交叉 | 多处 | 能力边界模糊 |

## 五、后续建议（可选，待确认后执行）

1. **统一资产检索挂载**：让 `search_assets` 只走一条路径（建议：勾选工具即生效，资产类型作为"可选范围过滤"而非"是否挂载的开关"），消除双轨。
2. **收敛 tool_search**：研判智能体等核心流程默认 `tool_search="off"` 或 `"auto"`，避免关键工具被隐藏。
3. **导航分层**：将侧边栏「智能体编排」拆分为「执行」（智能体/工作流）、「能力」（工具）、「内容」（技能/知识库）三层入口。
4. **内置工具打标**：在工具列表区分内置/自建，按 code/http/framework 分组展示。
5. **对齐工作流体系**：明确通用工作流与封禁触发规则的关系，或合并入口。
