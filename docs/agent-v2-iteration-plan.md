# 智能体体系大版本迭代方案（V2.0）

> 状态：**方案稿，待评审**。
> 适用对象：SOAR 平台「智能体编排」体系下的**智能体 / 工作流 / 技能 / 工具 / 知识库**。
> 目标：一次性解决四大痛点 —— ①工具杂乱无法统一管理 ②知识库未启用 ③技能/人物设定/智能体搭建繁琐杂乱 ④工作流创建没人使用。
> 前置：本文整合 `docs/architecture/module-responsibilities-and-relations.md`、`docs/discussion-agent-orchestration.md`、`docs/agent-construction-and-binding.md`、`docs/hermes-tools-migration-to-system.md` 的已有共识，统一为一份可执行规划。

---

## 一、现状与根因复盘

### 数据现状（soar_dev）
- 智能体：5（均 hermes 引擎）；工具：52（code 36 / framework 14 / http 2）；技能：11；工作流：1；知识库：0。

### 四大痛点的根因

| 痛点 | 根因 | 证据 |
|------|------|------|
| **工具杂乱、无法统一管理** | ① 内置工具与用户自建工具混淆，来源难辨；② 三类工具（code/http/framework）语义未对用户讲清；③ `search_assets` 存在工具表 + 资产类型双轨挂载，且工具表路径被 `continue` 跳过导致"配了不生效"；④ `tool_search` 动态隐藏关键工具 | `models/tool.py`、`seed.py` 的 `HERMES_BUILTIN_TOOLS`、`decision.py`、`tool_engine.py`、`tool_search.py` |
| **知识库未启用** | 引擎已支持检索工具（`search_knowledge_base`/`query_kb_file`），但库中知识库数量为 0，无内置可检索内容、无引导，用户不知道该建什么、怎么用 | `models/knowledge_base.py`、`kb_retriever.py`、`prompt_assembler.py` |
| **搭建繁琐杂乱** | ① 五大模块在导航平铺同层"智能体编排"下，概念层级不清（实为执行/能力/内容三层）；② `AgentEditor.jsx`（2656 行）为超大单体，集模型/提示词/技能/工具/知识库/资产类型/高级项/调试于一身；③ 技能/人物设定/工具/知识库需在不同页面分别维护后再回到智能体勾选 | `AppShell.jsx` 导航、`AgentEditor.jsx` |
| **工作流创建没人使用** | ① 通用工作流与封禁专用工作流（触发规则 `/ban-workflow/rules`）两套体系并存，概念混淆；② 工作流创建门槛高（需图形编排），无"AI 出初稿→人审阅固化"的低门槛入口；③ 缺少模板与使用引导 | `AppShell.jsx` 导航、`docs/discussion-agent-orchestration.md` |

## 二、总体设计目标

一句话：**把"散、乱、繁"的五个模块，收敛为一个「统一编排 + 向导式搭建 + 低门槛固化 + 可检索资产」的智能体体系。**

三个设计主轴：
1. **分层清晰**：前端导航按"执行层 / 能力层 / 内容层"分层，让用户一眼分清"谁编排、谁能干、谁知道"。
2. **统一管理**：所有工具（含内置/框架/安全）统一入库、统一可见、可打标、可搜索，消除双轨与隐式挂载。
3. **向导 + 闭环**：智能体搭建由"满屏表单"改为"分步向导";新增"AI 出初稿→人审阅→保存固化（技能/模板/工作流）"的低门槛闭环，让工作流和技能能被"生产"出来、被复用。

## 三、分模块迭代方案

### 模块 A：统一工具管理（解决"工具杂乱"）

**目标**：一个入口管理全部工具，来源可辨、语义清晰、挂载确定、可见可控。

**落地项**
1. **工具来源打标**：工具列表为每行显示来源徽章 —— 「内置 / 自建 / 框架」，并按 `code` / `http` / `framework` 分组收起展示。
2. **三类工具语义引导**：新建工具时提供类型选择引导卡片，讲清 code（写代码）、http（声明式接 API）、framework（框架内置动作）三者的区别与适用场景。
3. **消除 search_assets 双轨**：统一为"勾选工具即生效"，将 `enabled_asset_types` 降级为"可选范围过滤"而非"是否挂载的开关"；移除 `decision.py` / `tool_engine.py` 中对 `search_assets` 的 `continue` 跳过逻辑。
4. **收敛 tool_search**：研判类核心智能体默认 `tool_search="auto"`（或 `off`），避免威胁情报/封禁等关键工具被动态隐藏。
5. **工具健康度/使用统计**：展示每个工具的调用次数、失败率、最近使用时间，帮助清理死工具（为"统一管理"提供数据支撑）。

**关键文件**：`models/tool.py`、`api/v1/tools.py`、`api/v1/tools_manage.py`、`agent/hermes/tool_engine.py`、`agent/hermes/tool_search.py`、`agent/decision.py`、`core/seed.py`、前端 `ToolList.jsx` / `ToolEditor.jsx`。

### 模块 B：启用知识库（解决"知识库未启用"）

**目标**：让知识库从"0 数据、无用法"变为"有内容、有引导、被智能体真正检索"。

**落地项**
1. **建设内置知识库**：由平台侧沉淀 1~2 个开箱即用的知识库（如"安全运营响应规范""常用研判口径"），文档上传 → 分段/向量化走既有链路，让用户打开即有内容、可检索。
2. **添加知识库引导**：知识库页面新增空状态引导 —— "三步建库：上传文档 → 自动分段/向量化 → 在智能体中勾选启用"，并给出示例文档。
3. **启用联动提示**：在 `AgentEditor` 的知识库勾选处，显示每个库的文档数量/最近更新，未启用任何库时给出引导链接。
4. **检索可观测**：执行日志/调试面板展示知识库检索命中片段与来源，让用户直观看到"知识库生效了"。

**关键文件**：`models/knowledge_base.py`、`api/v1/knowledge_base.py`、`core/kb_service.py` / `kb_retriever.py` / `chunker.py` / `embedding.py`、`agent/hermes/tool_engine.py`、前端 `KnowledgeBase.jsx` / `AgentEditor.jsx`。

### 模块 C：向导式搭建 + 统一配置（解决"搭建繁琐杂乱"）

**目标**：把超大单体的 `AgentEditor` 拆为**分步向导**，并让"人物设定 / 技能 / 工具 / 知识库"的配置在统一心智下完成。

**落地项**
1. **导航分层**：将侧边栏"智能体编排"拆分为
   - **执行**：智能体、工作流（含触发规则）
   - **能力**：工具
   - **内容**：技能、知识库
   让层级一目了然。
2. **AgentEditor 重构为分步向导**（建议 4 步），拆解 2656 行单体：
   - ① 基础信息（名称/描述/头像/开场白）
   - ② 大脑与角色（选模型、写提示词、人物设定、语气/变量）
   - ③ 挂能力（工具 / 技能 / 知识库 / 资产类型，统一勾选面板）
   - ④ 行为与记忆（温度/轮数/记忆/工具行为/引擎选择）+ 调试
   每步可单独保存草稿，降低单屏认知负担。
3. **人物设定独立可复用**：将"人物设定/角色"从 `AgentEditor` 内联提示词提升为**可复用的内容资产**（复用 `Skill` 的"角色设定"分类），一个角色设定可被多个智能体引用，避免重复填写。
4. **从模板创建**：预置若干智能体模板（如"告警研判员""封禁决策员""资产分析员"），用户从模板一键创建再微调。

**关键文件**：前端 `components/AppShell.jsx`（导航）、`pages/AgentEditor.jsx`（向导拆分）、`models/agent.py`、`models/skill.py`。

### 模块 D：让工作流被用起来（解决"工作流创建没人使用"）

**目标**：降低工作流创建门槛，打通"AI 出初稿 → 人审阅 → 固化"，让标准化流程可被持续生产与复用。

**落地项**
1. **AI 出初稿 → 审阅 → 固化闭环**（承接 `discussion-agent-orchestration.md` 共识）：
   - 在智能体对话/调试中，用户用自然语言描述诉求 → AI 用 `plan` 工具生成结构化计划（步骤/tool/依赖）。
   - 前端提供「保存草稿」→ 进入草稿库（列表 + 简单编辑）。
   - 「定稿」后导出为**工作流**或**技能**（二选一，见待决项）。
2. **工作流模板库**：预置常用工作流模板（如"告警研判→封禁""定时巡检"），一键复制创建，避免从零拖拽。
3. **工作流体系对齐**：明确通用工作流与封禁触发规则的关系——把"触发规则"在导航上作为封禁工作流的**触发配置子项**呈现，消除两套体系的混淆。
4. **入门引导**：工作流列表空状态给出"从模板创建 / 让 AI 生成草稿 / 手动编排"三种入口。

**关键文件**：`models/workflow.py`、`api/v1/workflows.py`、`workflow/engine.py`、`agent/hermes/skill_engine.py`（触发工作流技能）、前端 `WorkflowEditor.jsx` / `WorkflowList.jsx` / `AppShell.jsx`。

## 四、统一资产心智（贯穿四模块）

建立一张"五模块关系"的统一认知，前端以**一张架构图 / 引导页**呈现给用户和开发者：

```
执行层  智能体(编排中枢) ← 工作流(节点编排，可调智能体/工具)
能力层  工具(可调动作: code/http/framework)
内容层  技能(教"怎么想"注入提示词) · 知识库(教"知道什么"生成检索工具)
```

- 智能体 → 引用：模型、技能、知识库、工具、资产类型
- 工作流 → 引用：智能体、工具
- 技能 / 知识库 / 工具 → 不引用彼此（均被上层引用）

## 五、落地节奏（建议分 4 个迭代）

| 迭代 | 范围 | 内容 | 验收标准 |
|------|------|------|---------|
| **V2.1 统一工具** | 模块 A | 来源打标、分组、语义引导、消除 search_assets 双轨、收敛 tool_search、使用统计 | 工具列表来源可辨、可分组；search_assets 单轨生效；关键工具不再被隐藏 |

## 七、风险与注意事项

- **AgentEditor 拆分**属于前端大改，建议以功能开关/路由渐进切换，避免一次性破坏现有编辑能力。
- **search_assets 双轨修复**涉及 `decision.py`（LangGraph）与 `tool_engine.py`（Hermes）两条路径，需回归测试研判类智能体。
- **内置知识库建设**需要实际安全运营内容素材，需业务侧提供。
- **工作流"AI 出初稿"需持久化 plan**：当前 `plan` 工具未持久化，需新增草稿存储（表或复用 execution 记录）。
- 所有变更需兼容既有数据（智能体 5 / 工具 52 / 技能 11），迁移以增量为主。

## 八、框架底座选型（新增，响应"用可行的框架代替原框架"）

### 8.1 关键事实：底层已是 LangGraph + LangChain
- `requirements.txt` 已依赖 `langgraph==0.2.39`、`langchain==0.3.4`、`langchain-openai/anthropic`。
- 现有自研「Hermes 引擎」实际是**在 LangGraph/LangChain 之上自造的一层"重型编排壳"**（`backend/app/agent/hermes/` 约 30 个文件，`executor.py` 1488 行、`tool_engine.py` 1046 行），实现了并行分段、委派、护栏(guardrails)、预算(budget)、工具检索(tool_search)、写操作验证、威胁扫描等高级能力。

**结论**：这些能力不是可以删掉的"乱"，而是**有价值的业务资产**。真正造成"散乱、繁琐"的，是把这些能力**暴露成了太多手工可见的配置概念**（工具/技能/知识库/资产类型/引擎/高级项……），以及一次性搬进超大单一表单。

### 8.2 选型建议：不推倒重换，而是"底座化收敛 + 引入成熟编排范式"

| 方案 | 说明 | 结论 |
|------|------|------|
| ❌ 整换重型平台（Dify / n8n / Flowise / Coze） | 自带 UI/编排/知识库，但需整套部署、重写业务对接；与现有 FastAPI + React + RBAC + 告警/封禁/审批链路深度耦合 | **不建议**：迁移成本与风险远大于收益 |
| ⚠️ 替换 LangGraph 为其它 agent 运行时（如 Autogen / CrewAI / Pydantic-AI） | 仅换推理编排层，业务保持不变 | **低收益**：现有 LangGraph 已满足，重写自研壳的代价高 |
| ✅ **保留 LangGraph/LangChain 为运行时底座，收敛自研壳为"标准底座 + 低代码配置"** | 把 Hermes 的高价值能力固化为**框架内建的、默认开箱即用**的底座；前端只暴露**分步向导 + 模板**，让"建智能体=选模板/填角色/勾能力"而非"配十个概念" | **推荐**（见 8.3） |
| ✅ **借鉴开源为底座注入标准化能力** | 引入/吸收成熟框架的轻量机制，提升底座可扩展性 | 可选（见 8.4） |

### 8.3 推荐路径：把"自研壳"沉淀为"标准底座"
1. **固化默认行为为底座默认值**：把 tool_search 收敛、guardrails、验证、并行、budget 等**设成平台级默认开启/自动**，智能体无需逐项配置即可获得可靠底座。用户聚焦"干什么"，而非"调什么参数"。
2. **智能体配置收敛为 4 个字段的心智**：`模型 + 角色(人物设定) + 勾选工具 + 可勾选知识库`。其余全部用底座默认 + 高级选项折叠。
3. **以"模板 + 向导"为唯一创建入口**（对齐模块 C/D），让专业领域处理 = 选一个"角色模板"（告警研判员 / 封禁决策员 / 资产分析员 / 自定义），再补工具与知识库即可。
4. **工作流/技能/知识库作为"底座资产"统一由智能体消费**，而非让用户在它们之间手工编排。

### 8.4 可选：可借鉴/引入的开源能力（按需选采）
只吸收**机制**、不整套换框架，避免重写：
- **LangGraph**：已用。可用其 `StateGraph`/`prebuilt` 重构 Hermes 的 `graph.py`，用官方稳定 API 替代自研边角，减少维护面。
- **Dify/Coze 的"应用模板 + 工作流可视化"心智**：借鉴其"应用=角色+工具+知识库"的一体化模型，指导我们合并多个入口。
- **CrewAI**：若需多角色协作（分析师+执行员+复核员），可借鉴其 Role/Agent 声明式模型，但不必引入其运行时。
- **LangChain Hub / 开源工具集**（如 `langchain-community` tools）：复用社区成熟工具接入，减少自研 code 工具量。

### 8.5 给"专业领域处理"的落地范式
每个专业领域 = **一个"角色模板（Skill 分类）+ 一组工具 + 可选的领域知识库 + 一个智能体实例"**。
- 建领域 → 复制通用模板 → 换角色设定（Skill"角色设定"）→ 勾选该领域工具/知识库 → 保存即得一个专用智能体。
- 底座把"模型调用、工具注册、检索、护栏、验证、记忆"全部自动接管，用户不再手动搭建。

### 8.6 迁移影响与风险
- 业务链路（告警、封禁、审批、资产、RBAC）不变，仅收敛"编排层暴露面"。
- `Agent` 表字段可保留做兼容（向后兼容），前端改向导；不强制删字段。
- 重大重构需以功能开关渐进切换，优先验证"研判/封禁"两条核心链路回归。

## 九、对外部框架评估：Pi Agent（earendil-works/pi）

> 本节针对你提出的 "piagent 项目"。GitHub 上同名项目很多，经排查，指向的主流项目是
> **Pi Agent Toolkit（[earendil-works/pi](https://github.com/earendil-works/pi)）**——
> 10.6 万 star、MIT、TypeScript，定位 "AI agent toolkit: unified LLM API, agent loop, TUI, coding agent CLI"。
> 如果你的 "piagent" 指的是别家仓库，请告知链接，我可再评估。

### 9.1 Pi 提供了什么
- `pi-agent-core`：**Agent 运行时**，带工具调用（tool calling）与状态管理（state）。
- `pi-ai`：统一多厂商 LLM API（OpenAI / Anthropic / Google 等）。
- `pi-coding-agent`：交互式编码智能体 CLI；`pi-tui`：终端 UI 库。
- `pi-telemetry`：供应商中立遥测；`chord`：应用组合运行时（服务/复制状态/RPC/插件）。

## 十一、内网部署约束下的落地收敛（对照你们环境）

> 你们是**内网服务器部署**。这意味着：**无法从公网 pip/npm 拉包、无法访问 openai 等外网模型 API**（需走内网模型网关/代理），
> 这直接决定了"引入开源项目"的方式必须是"**离线/内网源交付**"，且要避免引入依赖过重、离线打包困难的项目。

### 11.1 内网带来的硬约束
1. **依赖获取受限**：`pip install langflow` / `npm install` 需要公网或内网 PyPI/npm 镜像；项目一旦锁死版本，离线重装要能把整个依赖树一起交付。
2. **模型接入走内网网关**：OpenAI/Anthropic 外部 API 不可直连，需对接你们内网的 LLM 网关/代理（你们现已有 `LLMConfig` + `base_url` + `provider` 抽象，正好承接内网模型/base_url）。
3. **Docker 镜像传递**：跨机器（尤其跨架构，如 ARM64 服务器）不能直接 `docker save/load` 传递镜像，需在内网用同架构构建（你们 README 已写明此限制）。
4. **无法依赖托管服务**：Dify/n8n 等若有 SaaS/在线依赖的功能不可用，只能用可完整自托管的离线版本。

### 11.2 在内网前提下，三类开源项目的可达性

| 项目 | 内网可行性 | 关键点 |
|------|-----------|--------|
| **Langflow** | ✅ 可行（但要离线打包依赖树） | Python 生态，可在内网构建镜像；需 `--offline` 或预编译依赖上传内网 PyPI |
| **Dify** | ✅ 可行（自托管全离线） | 官方支持完全自托管 Docker Compose；依赖大、镜像多，要一次性把镜像打到内网 |
| **n8n / Flowise** | ⚠️ 可行但重 | Node 生态，n8n 镜像多、Flowise 依赖重，离线交付成本高；且与你们 Python 后端对接要另起服务 |
| **RAGFlow** | ⚠️ 可行 | 文档 RAG 底座，镜像较重（Elasticsearch/Infinity 等依赖），需判断内网资源是否够 |

### 11.3 内网下的最务实结论
- **首选路径仍建议 Langflow，但采用"离线构建镜像 + 内网镜像仓库"方式交付**：
  - 在**与服务器同架构**的一台构建机（或内网 CI）上用 `docker build` 构建 langflow 镜像 → 推到内网 registry → 服务器拉取。
  - 不用跨架构 `docker save/load`（避免 README 里踩过的 `exec format error`）。
- **次选 Dify**：如果你们更想要"完整一体、开箱即用"，Dify 支持完全离线自托管，把它的整套镜像拉到内网 registry 即可；代价是它是相对独立的体系，与你们 RBAC/告警/封禁深度集成成本高。
- **无论如何，模型都走你们内网 LLM 网关**：用 `base_url` 指向内网网关（OpenAI 兼容端点），Langflow/Dify 都能配置；这也正好复用你们现有的多模型配置经验。
