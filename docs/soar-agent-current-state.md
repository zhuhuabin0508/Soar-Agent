# SOAR 智能体现状全貌（决策前必读）

> 目的：把现有智能体这块"从数据到运行时"彻底讲清楚，让"替换 vs 优化"的决策有据可依。
> 这是先补足对现状的理解，不再空谈方向。

---

## 一、一句话血统认识（最关键）

**你们不是"没有智能体框架"，而是"自己造了一整层 Hermes 引擎，叠在 LangGraph 之上"。**
- `requirements.txt` 已依赖 LangGraph + LangChain（运行时底座）。
- `backend/app/agent/hermes/`（约 30 个文件）是在其上**自研的重型编排壳**，实现了一大堆高级能力（见第三节）。
- 你感觉"杂、乱、繁琐"，**根源不是没技术，而是这层自研壳把能力暴露得太散、配置概念太多**（工具/技能/知识库/资产类型/引擎/高级项……），且没有好的 UI 把复杂度收起来。

## 二、运行时全链路（一次对话发生了什么）

```
用户输入 → api/v1/agents.py:chat/test → HermesAgentExecutor.run (executor.py)
        → 组装 system prompt (prompt_assembler.py: 基础提示词 + 注入已启用技能)
        → 构建工具注册表 (tool_engine.py: DB工具 + 知识库检索 + 资产检索 + framework)
        → ReAct 循环 (_react_loop): LLM 想→调工具→看结果→再想
            ├─ 并行分段执行 (tool_dispatch: 并行段 gather / 顺序段串行)
            ├─ 护栏/预算/中间件 (guardrails / budget / middleware)
            ├─ 委派子代理 (delegator: delegate_task)
            ├─ 技能触发 (skill_engine: trigger_skill)
            ├─ 澄清 (clarify)
            └─ 校验写操作 (verification)
        → SSE 流式返回
```

### 运行时如何取到"人"（4 层能力本质，务必分清）
| 你配置的 | 本质 | 运行时去哪 | 会不会占上下文 |
|---------|------|-----------|--------------|
| 模型+温度/轮数 | LLM 实例 | 构造 LLM | — |
| 系统提示词 | 角色/总目标(文字) | 提示词正文 | 会 |
| 技能 enabled_skills | 教"怎么想"(文字) | 注入提示词"启用技能"段 | 会 |
| 知识库 enabled_kbs | 教"知道什么"(数据) | 生成检索工具 search_knowledge_base / query_kb_file | 不直接占 |
| 工具 enabled_tools | 能"做什么"(可调用) | 绑定为 LLM 可调工具 | 会(schema) |
| 资产类型 enabled_asset_types | 资产检索范围 | 生成 search_assets | 会 |

## 三、Hermes 引擎已实现的能力（= 有价值的资产，别轻易丢）

| 能力文件 | 功能 |
|---------|------|
| executor.py (1488行) | ReAct 主循环、流式、工具执行/拦截 |
| tool_engine.py (1046行) | 工具注册表 + 分段并行执行（并行 gather/串行）、不可信包装 |
| tool_dispatch.py | 工具并行/顺序分段规划 |
| tool_search.py | 动态工具检索/延迟挂载（BM25 目录）、bridge 工具 |
| guardrails.py | 工具调用护栏（越权/敏感操作拦截 + 恢复提示） |
| budget.py | 上下文/输出预算控制、结果截断持久化 |
| middleware.py | 审计/脱敏/限流/计时 中间件链 |
| delegator.py | 子代理委派（多 Agent 协作、深度限制） |
| skill_engine.py | 技能触发/恢复（流程技能注入与续跑） |
| clarify.py | 澄清提问 |
| verification.py | 写操作二次验证 |
| threat_scanner.py | 结果威胁扫描、注入检测 |
| redact.py / message_sanitization.py | 脱敏、不可信内容净化 |
| error_classifier.py / think_scrubber.py / sse.py | 错误分类重试、思考块剥离、SSE 事件 |

> 结论：**这套引擎能力很全**（委派、护栏、预算、检索、验证、威胁扫描、脱敏），达到商用级别。绝不是"骨架"，是"血肉"。真正的问题在**外面没包一层好用的壳**。

## 四、五大模块关系（为什么感觉乱）

```
执行层   智能体(编排中枢)  ←  工作流(节点编排，可调智能体/工具)
能力层   工具(可调动作)     ← 被智能体/工作流/技能引用
内容层   技能(怎么想) · 知识库(知道什么)  ← 被智能体注入/检索
```

- **谁引用谁**：智能体→(模型/技能/知识库/工具/资产类型)；工作流→(智能体/工具)；技能/知识库/工具→不引用彼此，都被上层引用。
- **"乱"的本质**：这五个模块**本不属于同一层**，却在导航里平铺在"智能体编排"下，造成"好像都该一起配，又不知谁是谁"的认知负担。
- **两套工作流**：通用工作流 和 封禁专用工作流(触发规则 /ban-workflow/rules) 是两个独立体系，易混淆。
- **search_assets 双轨**：既在工具表又有资产类型直挂，且工具表路径会被跳过 → "配了不生效"。

## 六、这决定了"替换 vs 优化"怎么选

| 事实 | 含义 |
|------|------|
| 底层已是 LangGraph + LangChain | 运行时底座是成熟开源的，无需换 |
| Hermes 里是大量高级能力（委派/护栏/预算/检索/验证/扫描） | 是资产，替换会**连这些能力一起丢**，重建成本极高 |
| "乱/繁琐"来自暴露面太散 + 无好 UI | 属于**可修的问题**（收敛配置 + 做向导/模板/草稿闭环），不是"框架不行" |
| 内网部署，约束大 | 引入重型外部平台（Dify 等）成本高、离线交付难 |

### 结论
- **倾向"优化/收敛现有 Hermes"**：因为推翻重做的最大损失是丢掉 Hermes 里这 12+ 项高级能力，而"乱"的本质（暴露面散、无好壳）是**可以不推倒就修好**的。
- **替换**的合理触发条件：只有当你想**连运行时能力都换掉**（比如彻底不要 LangGraph、要别国框架），或现有引擎与你的新架构完全不兼容时，才值得——但成本很高、风险大。

> 但如果你的目标就是"推倒重来，用全新思路做一套更简单的智能体"，那也可以，只是要接受：**把 Hermes 的成熟能力重新实现一遍**，或**接受新底座没有这些能力**。
